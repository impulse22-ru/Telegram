# Полный тех-план: TikTok-сервис + магазины поверх Telegram (сервер за границей)

## Итоговая архитектура

```
┌─ КЛИЕНТ: форк этого репо (страна блокировки) ─────────────────┐
│  • Штатный MTProto-логин пользователя (свой Telegram-аккаунт)  │
│  • Кастомный экран ленты (TikTok-style, swipe/автоплей)        │
│  • Кастомные AI-фичи поверх UI                                │
└──────────────┬────────────────────────────────────────────────┘
               │ (1) MTProto через прокси-транспорт вашего сервера
               │ (2) HTTPS-запросы к вашему API (лента, мета, команды)
               ▼
┌─ ВАШ СЕРВЕР за границей ──────────────────────────────────────┐
│  MTProxy/транспорт   → прячет MTProto, даёт доступ к DC       │
│  Bot API (бот-админ) → читает содержимое каналов ЛЕГАЛЬНО      │
│  API + worker        → лента, магазины, фильтрация, аналитика  │
│  БД: PostgreSQL + Redis                                        │
└──────┬────────────────────────────────────────────────────────┘
       │ MTProto / Bot API
       ▼
  Telegram DC (каналы-хранилища: видео и товарные каталоги)
```

**Базовая идея:** пользователь логинится своим Telegram-аккаунтом,
но сеть к Telegram идёт через ваш сервер (для обхода блокировки),
а серверная логика (лента, фильтрация, аналитика) построена на
Bot API — бот является администратором закрытого канала и читает
его контент легально, без взлома end-to-end шифрования сессий
пользователей.

## 1. Авторизация и доступ к каналу

### Штатный логин (безопасный путь)
- Пользователь вводит телефон → код → клиент (форк) логинит его аккаунт
  штатным MTProto-флоу, из этого репо (без изменений протокола).
- Сессии хранятся локально на устройстве пользователя, сервер их НЕ видит.
- Все соединения клиент делает через MTProxy вашего сервера (нативная
  поддержка прокси уже есть в `ConnectionsManager` / настройках).

### Автоматический доступ к закрытому каналу
1. Канал приватный, бот — админ канала.
2. После первого логина клиент вызывает ваш API `POST /v1/join` с
   `chat_id` канала и user_id пользователя.
3. Сервер через Bot API добавляет пользователя в канал автоматически
   (`inviteChatMembers`) с правами «только чтение».
4. Результат возвращается в клиент, лента активируется.

Возможный вариант допуска для фанатских каналов: бот настраивается
на автоподтверждение заявок (`MyChatMember` → approve) — пользователь
жмёт «Вступить» прямо в клиенте, без API.

## 2. Сервер (VPS за границей)

- **Провайдер:** Hetzner Cloud (Франкфурт) или DigitalOcean/Vultr
- **Старт:** 2 vCPU, 4 ГБ RAM, 40 ГБ NVMe (~5–8 €/мес)
- **ОС:** Ubuntu 22.04 LTS
- **Security:** SSH только по ключу, fail2ban, ufw (22, 80, 443, MTProxy-порт),
  непривилегированный пользователь
- **Snapshot:** ежедневный бэкап; резервный VPS у другого провайдера
  на случай блокировки IP

## 4. Как сервер видит видео канала (Bot API)

Бот — администратор закрытого канала. Содержимое читается легально
через Bot API:

- `getUpdates` / `editMessageMedia` → пришедшие видео от админов канала
- `getChat(chat_id)` → метаданные
- `forwardMessage`, `sendVideo`, `sendPhoto` → кастомные команды
- Медиа хранятся на сервере Telegram: Bot API отдаёт `file_id`,
  загрузка байтов через `getFile` → `filePath`.
- Для видео аналитики/фильтрации достаточно метаданных и превью
  (качать байты целиком не обязательно).
- Для больших файлов: оставляем файлы в Telegram, клиент-форк тянет
  их штатно (он участник канала) — двойной трафик не нужен.

### Локальный Bot API сервер (обход лимита 50 МБ)

Облачный Bot API ограничивает **загрузку 50 МБ** и **скачивание 20 МБ**.
Чтобы бот мог загружать/скачивать файлы до **2 ГБ**, поднимаем
официальный локальный Bot API сервер (`tdlib/telegram-bot-api`)
на нашем VPS:

| | Облачный Bot API | Локальный Bot API (`--local`) |
|---|---|---|
| Загрузка файла | до 50 МБ | **до 2000 МБ** |
| Скачивание файла | до 20 МБ | **до 2 ГБ** |
| Транспорт | через инфраструктуру Telegram | MTProto напрямую |

```bash
git clone https://github.com/tdlib/telegram-bot-api
cd telegram-bot-api && docker build -t telega-bot-api .

docker run -d --name bot-api \
  -p 8081:8081 \
  -v /var/lib/bot-api:/var/lib/telegram-bot-api \
  telega-bot-api \
  --api-id=<API_ID> --api-hash=<API_HASH> \
  --local \
  --dir=/var/lib/telegram-bot-api
```

Свой бот переключаем на `http://localhost:8081/bot<TOKEN>/...`.

**Использование лимитов в сценариях:**
- Товары в магазинах (большие файлы) → локальный Bot API (`--local`)
- Видео в ленте клиента → клиент-форк качает напрямую по MTProto (2 ГБ)
- Аналитика/модерация → только метаданные + превью (качать не нужно)

**Лента:** сервер периодически (`getUpdates`) индексирует новые видео
канала в PG + Redis. Порядок и подборки отдаёт клиенту через API;
клиент проигрывает видео напрямую из канала (быстро, без прокси
для медиа).

## 6. База данных (PostgreSQL)

```sql
users(id, tg_user_id, phone, name, created_at)
channel(id, tg_chat_id, title, is_private)          -- наш закрытый канал
videos(id, tg_msg_id, file_id, caption, duration_ms,
       width, height, title, tags text[], status,     -- 'visible'|'banned'
       channel_id, posted_at)

comments(id, user_id, video_id, text, parent_id, created_at)
views_log(user_id, video_id, watch_seconds, created_at)  -- аналитика
subscriptions(user_id, channel_id, created_at)

-- === МАГАЗИНЫ ===
shops(id, owner_id, tg_chat_id, title, description,
      payment_info,            -- СБП/крипта-реквизиты продавца
      status)                  -- 'active' | 'suspended'
products(id, shop_id, tg_msg_id, file_id, title, description,
         price_amount, price_currency,
         category, status,     -- в наличии / снят
         posted_at)

       price_amount, price_currency,
       payment_status,         -- 'pending' | 'paid' | 'confirmed' | 'cancelled'
       contact_details,        -- телефон/адрес доставки от покупателя
       created_at)
order_chat_link(id, order_id, tg_chat_id)  -- чат покупатель-продавец после оплаты
```

## 7. Магазины и фичи для бизнеса

### Создание магазина (любым пользователем)
1. Пользователь в клиенте вызывает `POST /v1/shop` → сервер через бота
   создаёт новый канал-магазин (или привязывает существующий), бот
   добавляется админом.
2. Владелец получает права продавца, магазин появляется в каталоге
   сервиса (`GET /v1/shops`).
3. Товары — посты в канале с форматом:
   `📦 Название | Цена: 500 ₽ | Категория | #теги`
   Бот индексирует посты и подтягивает их как карточки в витрину.

### Корзина и заказ
1. В ленте товарная карточка → «Купить» → `POST /v1/order`.
2. Сервер создаёт `order` со статусом `pending`, присылает покупателю
   в клиенте форму контактов (телефон/адрес).
3. После отправки данных продавцу доставляется уведомление
   (в его канал-чат), покупателю — `payment_info` (СБП/крипта-реквизиты).
4. Продавец подтверждает оплату вручную или автоматически
   (`payment_status → confirmed`), открывается контактный чат
   `order_chat_link`.

### Фичи для бизнеса
| Фича                     | Реализация                                             |
|--------------------------|--------------------------------------------------------|
| Витрина в ленте          | товарные карточки в общей TikTok-ленте + фильтр `shops`|
| Аналитика продаж         | дашборд: просмотры/заказы/выручка по `orders+views`    |
| Уведомления о заказах    | бот пишет продавцу и покупателю на каждом переходе     |
| Модерация магазинов      | жалобы, приостановка `status='suspended'`              |
| Кастомные команды        | `!promo`, `!stat`, `!pin` — через бота по расписанию

### Оплата (внешняя — СБП/крипта)
- Telegram/Payments Б НЕ используется (реальные деньги не в мессенджере).
- Сервис передаёт `payment_info` продавца, подтверждение оплаты
  происходит вне клиента (скриншот/чек/ввод кода) или автоматически
  по webhook крипто-эквайринга (опционально).
- Юридическая модель: платформа — агрегатор-витрина, продавцы отвечают
  за сделки (пользовательское соглашение в разделе «Риски»).

## 8. Алгоритм ленты (скоринг)

```
score = 0.6 * likes_velocity(24h) + 0.25 * comments_velocity(12h)
      + 0.15 * view_time_normalized - 0.5 * log(1 + hours_since_upload)
```

Redis: `zadd feed {ts:score} {video_id}`, выдача `zrevrange` с пагинацией.
Фильтрация: при зда-выдаче исключать `status='banned'` и автора в чёрном списке.
Товарные карточки в ленте имеют свой скоринг-тип с поправкой на `price`/`category`.

## 9. API (клиент ↔ сервер)

| Method | Path                       | Описание                                |
|--------|----------------------------|-----------------------------------------|
| POST   | /v1/auth/telegram          | регистрация user_id после логина в клиенте |
| POST   | /v1/join                   | автоматическое вступление в закрытый канал |
| GET    | /v1/feed                   | лента с пагинацией                      |
| GET    | /v1/videos/{id}            | метаданные видео                        |
| POST   | /v1/videos/{id}/like       | лайк/дизлайк                            |
| POST   | /v1/videos/{id}/comments   | комментарий                             |
| POST   | /v1/videos/{id}/report     | жалоба → модерация                      |
| GET    | /v1/stats/{user}           | аналитика просмотров (админ)            |
| POST   | /v1/custom/{command}       | кастомные команды бота                  |
| POST   | /v1/shop                   | создать магазин (канал)                 |
| GET    | /v1/shops                  | каталог магазинов                       |
| POST   | /v1/product                | добавить/изменить товар                 |
| POST   | /v1/order                  | оформить заказ                          |
| GET    | /v1/order/{id}             | статус заказа (обновления через WS)     |
| POST   | /v1/order/{id}/confirm     | подтверждение оплаты (продавец)         |
| GET    | /v1/orders/seller          | заказы продавца (аналитика, статусы)    |

Авторизация: JWT access (15 мин) + refresh (30 дней). Роли: user / admin.
Клиент: после логина в Telegram вызывает `/v1/auth/telegram` с
`user_id` и `auth_hash` (подпись) → получает JWT.

## 9. Устойчивость к блокировкам

- Несколько фолбэк-доменов (app1.domain, app2.domain) с TTL 60 сек
- Клиент фолбэчется автоматически при ошибке соединения
- MTProxy-порт при блокировке меняется (или используется мешанина
  fake-TLS: `ConnectionSocket.cpp` в репо умеет)
- Резервный VPS + snapshot: при блокировке IP — новый инстанс за час
- Опционально: Cloudflare перед API

## 10. Мониторинг и бэкапы

## 13. Ключевые риски

1. **Бан аккаунта-канала** — аккуратная публикация, лимит публикаций/день,
   не спамить командами
2. **Блокировка MTProxy/IP** — быстрое переключение порта/IP, резервный VPS
3. **Нелегальный контент** — контент-модерация + фильтрация, жалобы
4. **Злоупотребления** — rate-limit на like/comment/report, капча при регистрации
5. **Торговые риски** — мошенничество продавцов: жалобы, приостановка магазинов,
   пользовательское соглашение, отказ от ответственности платформы за сделки
